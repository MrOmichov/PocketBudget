# База данных после V5

Источник истины — SQL-файлы в src/main/resources/db/migration.
[Справочный SQL-снимок](schema.sql) показывает итоговую схему; это не миграция.

~~~mermaid
erDiagram
    users ||--o{ expenses : owns
    categories ||--o{ expenses : classifies
    users {
        bigint id PK
        varchar username UK
        text password_hash
        boolean enabled
    }
    categories {
        bigint id PK
        text name UK
    }
    expenses {
        bigint id PK
        bigint user_id FK
        bigint category_id FK
        bigint amount
        date spent_at
    }
~~~

Один пользователь — много расходов. Одна общая категория — много расходов.
Каждый расход обязан иметь одного владельца и одну категорию. Все пользователи используют общую таблицу expenses.

| Таблица | Поле | Ограничение / смысл |
|---|---|---|
| users | id | bigint PK, GENERATED BY DEFAULT AS IDENTITY |
| users | username | varchar(50) NOT NULL UNIQUE; регулярное выражение ^[a-z0-9_]{3,50}$ |
| users | password_hash | text NOT NULL; хеш PasswordEncoder |
| users | enabled | boolean NOT NULL DEFAULT true |
| categories | id | bigint PK, GENERATED BY DEFAULT AS IDENTITY |
| categories | name | text NOT NULL UNIQUE; минимум один непробельный символ |
| expenses | id | bigint PK, GENERATED BY DEFAULT AS IDENTITY |
| expenses | user_id | bigint NOT NULL, FK → users.id, ON DELETE RESTRICT |
| expenses | category_id | bigint NOT NULL, FK → categories.id, ON DELETE RESTRICT |
| expenses | amount | bigint NOT NULL CHECK amount > 0; копейки |
| expenses | spent_at | date NOT NULL; в Java LocalDate |

Имена категорий уникальны с учётом регистра; food и Food различаются. Автоматического trim или lower нет.

## Удаление и доступ

FK не позволяет удалить используемую категорию или пользователя. Удаление расхода не удаляет ни пользователя, ни категорию: JPA REMOVE-каскады на этих связях отсутствуют.

FK проверяет существование владельца, но не права вошедшего пользователя. Доступ ограничен запросами приложения: список по user_id, отдельный расход по id вместе с user_id.

## Индексы

PK и UNIQUE создают индексы.
Дополнительно есть expenses_user_date_id_idx на (user_id, spent_at DESC, id DESC): соответствует выборке владельца с сортировкой.
Отдельного индекса только на category_id сейчас нет.

## История

| Версия | Изменение |
|---|---|
| V1 | expenses со строковым полем category |
| V2 | categories, перенос имён, заполнение category_id, FK, удаление старого category |
| V3 | food, transport, other без дублирования имён |
| V4 | users |
| V5 | Отключённый legacy, назначение старых расходов, user_id, FK и индекс |

legacy — служебный отключённый аккаунт для исторических расходов, не готовый пользователь для входа.
Flyway ведёт дополнительную служебную таблицу flyway_schema_history.

## Проверка через psql

~~~sql
SELECT current_database();

SELECT e.id, e.amount, e.spent_at, u.username, c.name AS category
FROM expenses e
JOIN users u ON u.id = e.user_id
JOIN categories c ON c.id = e.category_id
ORDER BY e.id;

SELECT version, description, type, success
FROM flyway_schema_history
ORDER BY installed_rank;
~~~
